Featured case study / Cloud operations + AI

OpsBridge Cloud Operations & AI Investigation.

I designed, built, tested, and operated a connected internal platform for a hybrid AWS and Azure environment. It brought infrastructure knowledge, controlled PowerShell tools, and AI-assisted incident investigation into the team's daily workflow.

01 / Why it mattered

Three recurring problems. One deliberate system.

The work began with a practical observation: engineers had to gather context, run routine actions, and investigate incidents in different places. I built a platform around those three connected jobs.

01

Infrastructure knowledge

Manually maintained documentation made it hard to find a dependable view of the current AWS and Azure environment.

02

Operational work

Routine administration relied on direct server access and scripts that were difficult to discover, standardize, and audit.

03

Incident triage

Engineers gathered Windows and cloud evidence from several consoles before they could form a useful diagnosis.

02 / The platform

A connected operating surface.

PowerShell 7 and Pode provide the web and automation foundation. The browser interfaces connect three capabilities while keeping their responsibilities clear.

Pillar 01 / Know

Documentation generated from the estate.

Read-only collectors use AWS CLI and Microsoft Graph to produce JSON and Markdown records. The documentation portal adds in-memory search, resource views, and diagrams so engineers can find context without relying on an individual's memory.

The same structured records provide a grounding corpus for the platform's AI agents. A refresh updates the knowledge base from the source systems.

Pillar 02 / Act

Tools that meet engineers where they work.

The Tools Portal presents operational PowerShell tools through forms generated from each tool's manifest. New tools can be discovered without changing the portal interface.

Actions run in the authenticated user's context. Confirmation gates protect changes, while execution history and audit records make work traceable.

Pillar 03 / Investigate

AI grounded in operational evidence.

An incident investigation agent on Azure AI Foundry Agent Service assembles Windows and AWS evidence before asking a model to analyze it. A second assistant answers infrastructure questions from generated documentation.

The design keeps evidence collection under program control and treats model output as an analysis to verify, with citations and explicit uncertainty.

03 / The AI workflow

Evidence first. Analysis second.

The investigation agent was the hardest part to get right: useful output depended on collecting the right evidence and refusing unsupported certainty.

  1. 01 / Route

    Classify without a model call

    A local router selects an incident domain and its evidence plan before Azure AI Foundry is involved.

  2. 02 / Collect

    Gather evidence in parallel

    Registered collectors inspect relevant Windows state through WinRM and AWS telemetry through cloud APIs. The platform records successful, partial, and failed collection.

  3. 03 / Analyze

    Give the model a bounded task

    The Foundry agent receives the collected evidence and produces a structured summary, likely cause, and recommended next steps within a limit of two model calls per investigation.

  4. 04 / Verify

    Check citations and confidence

    Claims must cite evidence actually collected. Coverage across identity, current state, timeline, and changes limits confidence when evidence is incomplete or targets are unresolved.

Learning loop

Confirmed root-cause analyses can be archived with deduplication for retrieval in later investigations. Generated cloud documentation supplies the other part of the grounded knowledge base.

04 / Engineering ownership

Built across the full stack. Operated with care.

As the solo engineer, I worked from architecture and interface design through cloud integration, agent behavior, testing, and day-to-day operation.

Architecture

PowerShell services, Pode web interfaces, API routes, browser interactions, and file-based JSON/Markdown storage.

Cloud integration

Read-only AWS and Azure collection, Windows diagnostics, and Azure AI Foundry Agent Service.

Security

AD authentication, per-user execution, DPAPI-protected secrets, confirmation gates, and audit trails.

Quality

Offline Pester contract tests for evidence envelopes, function dispatch, citation integrity, confidence policy, and persistence.

Operations

Auto-start, health checks, structured logging, and recovery paths for the internal production service.

Cost discipline

Local routing and evidence collection before model analysis, with explicit limits on calls and operation budgets.

What changed

Cloud context, routine action, and incident analysis now share a more coherent workflow.

The platform gives engineers searchable documentation, guarded self-service tools, and evidence-backed incident reports in one connected system.

05 / Engineering decisions

Trade-offs made explicit.

These choices fit an internal operations platform. They also define what I would revisit as usage and requirements change.

Lightweight local storage

JSON and Markdown files kept deployment simple and made generated documentation inspectable. Greater concurrency or multi-instance scaling would call for a database and stronger transaction handling.

Deterministic collection before model analysis

Local routing and parallel collectors gather relevant evidence before bounded Foundry calls. This controls cost and makes the inputs reviewable, but the chosen evidence plan can miss an unfamiliar failure mode.

Uncertainty stays visible

Partial collection or unresolved targets lower confidence and require engineer verification. Cited findings and recommendations support diagnosis; they do not trigger autonomous remediation.

Tests validate contracts

Offline Pester tests cover evidence shape, dispatch, citations, and confidence rules. Passing them does not guarantee that a model's proposed root cause is correct in a live incident.
